## 1. 结论：那个"老 bug"是什么

`SetWindowRgn` 的坐标**同时**受两件事影响，而老代码只处理了其中一件、而且是在错误的前提下：

| 事实 | 数值（真机实测） |
| --- | --- |
| Electron `getBounds()` / `getContentSize()` / 页面 `innerWidth/innerHeight` | **422×602**（DIP/CSS），`devicePixelRatio=1.5` |
| Win32 `GetWindowRect` | **632×902**（物理像素）= 422×602 × **1.5** |
| 显示器 | 2560×1600 物理，`scaleFactor=1.5`，工作区 1707×1019 CSS |
| PowerShell 辅助进程默认 DPI 感知 | **0 = UNAWARE** |

**病根**：辅助进程是 DPI-unaware 的，Windows 会把它交给 `SetWindowRgn` 的坐标
**再乘 1/1.5 = 0.667**。老代码按"CSS→物理"乘了 1.5，然后被系统又乘 0.667 ——
两个错不抵消（1.5 × 0.667 = 1.0 看着像抵消了，但**区域和窗口用了不同的坐标系**），
结果区域整体偏移 + 被窗口剪裁，表现为"只裁到她一部分 / 和她的位置对不上"。

老注释里那句 **「实测区域 = 期望 × 0.667」就是这条**，只是当时把方向理解反了。

### 标定证据（`tools/probe/probe-rgn-cal*.ps1`）

在一个 400×400 的 WS_POPUP 窗口上请求区域，再回读：

| 请求 | 未声明 DPI 感知 | 声明 DPI 感知后 |
| --- | --- | --- |
| (0,0)-(100,100) | (0,0)-(67,67) | (0,0)-(100,100) |
| (100,100)-(200,200) | (66,66)-(133,133) | (100,100)-(200,200) |
| (200,300)-(300,400) | (133,200)-(200,267) | (200,300)-(300,400) |

→ 未声明时**一律 ×0.667**；声明后**一律 1:1、零偏移**。

### 另外还踩了一个"仪器"坑（重要）

`probe-rgn-exact.ps1` 自己也是 DPI-unaware 时，**它读回的区域是它自己虚拟化过的逻辑坐标**
（物理值 ÷1.5）。于是它把一个**完全正确**的区域报成"缩小了 0.667 倍"，
让我一度以为 `SetWindowRgn` 本身会缩放。**探针必须先声明 DPI 感知**，
这条已写进探针头部注释，别再删。

## 4. B 方案的最新实测（下一步要用的数）

| 量 | 值 |
| --- | --- |
| 窗口 | 422×602 CSS（632×902 物理） |
| 她本人（tight） | ≈ **195×172 CSS** |
| 区域（含 expand=24） | ≈ **243×220 CSS** |
| 工具栏 | 她下方，高 34 CSS（`dockClearance()=34×--dshp-s`） |
| 菜单 | **硬编码 `width:360px!important`**、高 `min(300px, 100vh-200px)`（`pet.js:674`） |
| 简报面板 | `min(352px, 100vw-30px)`（`pet.js:636`） |
| 气泡 | `min(300px*--dshp-s, 70vw)`（`pet.js:585`） |

### 关键矛盾（B 为什么没那么简单）

菜单是 **360 宽 × ~300 高**，而窗口只有 602 高、她占 344~553。
菜单贴在她头顶（`.dshp-panel` 在 root 里 `bottom:100%`）→ 必须放在她上方。

要真的"零死区"，窗口就得**同时**装下：菜单 300 高 + 她 209 高 + 工具栏 34 高 ≈ 543 高，
**宽度还得 ≥360（菜单）**，而她只占 240 宽 —— 也就是：
**要么把菜单压窄到 ~200（改 UI 观感），要么把窗口做成 L 形（成型又回来了）。**

### 三条可选落地路径（建议按此顺序试）

1. **压窄菜单 + 窗口收到 ~260×330 CSS**
   - `.dshp-menu` 的 `width:360px!important` 改成 `min(360px, calc(100vw - 16px))`；
     气泡的 `70vw` 已经会自动跟着缩。
   - 她 `top:344 → ~86`，即窗口高度 602 → ~330。
   - 菜单仍然"在她上方"（`bottom:100%`），但纵向空间会紧张 → 高度公式也要改小。
   - 死区基本消失（左上只剩菜单右侧那一小块，且只在菜单关着时是空气）。
2. **面板改成"向下弹"**（交接文档原话的方向）
   - 她挪到窗口上部、面板在她下方展开；`clampPet` 的 `PET_BODY.offB` 与
     `clampY`（`pet.js:1929`）都要按新布局重算，否则贴屏幕下沿时面板会出屏。
   - 改动量最大，但语义最干净。
3. **保持现状**（成型关、接受左上角挡鼠标）
   - 零风险。`pos.json` 的位置记忆仍然形同虚设（启动被 `clampPet` 钉右下角），可另修。

**我的建议：先做 1（一天内可验证），不行再上 2。**

## 6. 新踩的坑（别重复）

1. **探针自己也要声明 DPI 感知**，否则区域被读成逻辑坐标，会把正确的区域误报成"缩小 0.667 倍"（这次绕了好几圈）。
2. **`.ps1` 必须带 UTF-8 BOM，或者干脆全 ASCII**。PS 5.1 把无 BOM 的 UTF-8 当 ANSI 读，
   中文会把引号吃掉 → 语法错误。**写文件的工具会丢 BOM**，所以最稳的是**纯 ASCII 脚本**
   （`probe-rgn-exact.ps1` 已经把中文标题改成用 `(char)0x9CB8...` 拼出来）。
3. **别用 `Get-Process` 找桌宠进程**：它有时看不见（但 `EnumWindows` 能按标题找到窗口）。
   找窗口请用 `list-windows.ps1`，或直接用 boot.log 里的 `hwnd`。
4. **`[System.Diagnostics.Process]` 的 `MainWindowTitle` 对 Electron 常为空** → 别用它判断。
5. **Electron 的 `getBounds()` 是 DIP、`GetWindowRect` 是物理像素**，
   同一窗口在这两个 API 下**天生差一个 scaleFactor** —— 不要以为哪个"错了"。
6. **本机沙箱下 node 用管道抓子进程 stdout 会 EPERM**（`measure-mask-units.mjs` 因此跑不动）。
   要量页面侧几何，只能让壳自己把数写进 boot.log。
7. 改生成物前先确认它是不是生成物：`main.js` / `preload.js` / `window-shape.cjs` / `server.cjs`
   **都是**；生成器现在在 `tools/shell-gen/`（以前只在作者的 `_staging/`，已搬进仓库）。这次先改生成器再重新生成，全程没被覆盖。
