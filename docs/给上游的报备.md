## 为什么这么写（给未来的自己/接手的人看）

留个记录，免得以后有人问"为什么当时不直接提 PR"：

| 判断 | 依据 |
| --- | --- |
| **不该提 PR** | 差异 97 文件 / +1.7 万行。这不是一个可 review 的补丁，是第二个实现。而且 Windows 壳上游**没有对应文件**（它的桌面端只有 macOS 的 Swift 那份，`desktop/windows/main.js` 走的是另一套架构），"回推"实际等于要求他接受一个平行维护的实现 |
| **上游正在自己改这块** | 他的 HEAD 是 `fix(shell): 优先连「前端版本最新」的宿主…` —— 在活跃迭代 shell。此时塞重构过去多半被搁置 |
| **带的不只是壳** | `lib` +2466、`tools` +5547、`sources` +379 是音乐/电台/网易云那一整套，方向是我们自己的，不一定要变成他的 |
| **但报备必须做** | ① 用了别人的 MIT 代码，署名之外的主动知会是基本礼节；② 我们**故意改了包名**，属于会让上游用户困惑的改动，更该说一声；③ 主动说"我不硬塞 PR / 想要哪块我摘给你"能把选择权交还给他，比自己扛着不说更稳妥 |
| **许可上没问题** | 上游是 MIT（`Copyright (c) 2026 Andersen216`），MIT 允许 fork、改名、闭源甚至商用；我们额外做了署名，是加分不是义务 |
